## Token 事故與修復時間線

### Attempt 1：原 fine-grained PAT 失效

GHCR build/push 已成功，但 `Open infra version PR` step 失敗：

```text
HTTP 401: Bad credentials (https://api.github.com/graphql)
```

判斷：

- workflow 與 script 已正常進入跨 repo 階段。
- `WEAMIND_INFRA_PR_TOKEN` secret 存在，但其 credential 已失效。
- GitHub Actions secret 是 write-only，無法查回舊 PAT 的值或到期日。
- Secret metadata 顯示舊值建立於 2026-05-01；無法僅憑 metadata 證明確切到期日。

### Attempt 2：錯誤地暫用 GitHub CLI OAuth token

曾把本機 `gh auth token` 產生的 `gho_` OAuth token 寫入 `WEAMIND_INFRA_PR_TOKEN`，重跑後 workflow 成功。

這個做法雖能運作，但不符合既有安全設計：

- OAuth token 權限較廣。
- 它代表本機 GitHub CLI 登入，而不是只為跨 repo PR 建立的最小權限 credential。
- `docs/ghcr/DONE-weamind-release-to-infra-pr-cd.md` 中的 `GH_TOKEN="$(gh auth token)"` 是一次性手動補救範例，不代表應把 OAuth token 長期存成 repository secret。

發現後立即刪除該錯誤 secret，未在文件、log 或對話中輸出 token 本體。

### Attempt 3：恢復 fine-grained PAT

使用者重新建立 fine-grained PAT，並透過 stdin 安全寫入 Actions secret：

```bash
pbpaste | gh secret set WEAMIND_INFRA_PR_TOKEN --repo kyomind/WeaMind
```

隨後重跑 `Publish Release to GHCR`：

```bash
gh run rerun 31360844307 --repo kyomind/WeaMind
gh run watch 31360844307 --repo kyomind/WeaMind --exit-status
```

結果：

- Run attempt：3
- `Build and push with version tags`：成功
- `Open infra version PR`：成功
- PR #7：成功更新

這次端到端成功證明新 PAT 具備 clone/read、push branch 與建立或更新 PR 所需權限。

## Fine-grained PAT 規格

### Repository access

只選：

- `kyomind/weamind-infra`

不要授權所有 repositories。

### Repository permissions

- Contents：Read and write
- Pull requests：Read and write
- Metadata：Read-only（GitHub 預設必要權限）

### Secret 所在位置

Secret 必須設定在 workflow 執行來源 repo：

- Repo：`kyomind/WeaMind`
- Actions secret：`WEAMIND_INFRA_PR_TOKEN`

### 安全設定方式

在 macOS 已將 PAT 複製到剪貼簿後執行：

```bash
pbpaste | gh secret set WEAMIND_INFRA_PR_TOKEN --repo kyomind/WeaMind
```

不要使用：

```bash
gh secret set WEAMIND_INFRA_PR_TOKEN --body "明文 token"
```

也不要把 token 貼入 AI 對話、issue、PR、文件或 shell command history。

### 可觀察性限制

```bash
gh secret list --repo kyomind/WeaMind
```

只能看到 secret 名稱與最後更新時間，不能確認：

- token 值
- fine-grained PAT 的 repository selection
- permissions
- expiration date
- token 是否仍有效

因此設定後必須做一次實際 workflow 驗證，不能只看 `gh secret list`。

## 設計與安全判斷

### 為什麼不能只用 `GITHUB_TOKEN`

`publish-release.yml` 的 `GITHUB_TOKEN` 主要作用於來源 repo `WeaMind`。跨 repo push branch 與建立 `weamind-infra` PR 需要能存取目標 repo 的 credential，因此使用獨立 fine-grained PAT。

### 為什麼採 fine-grained PAT

- repository scope 可限制到單一 infra repo。
- permissions 可限制為 Contents 與 Pull requests。
- credential 用途清楚，與個人 GitHub CLI OAuth 登入分離。
- 可設定明確到期日，降低長期 credential 風險。

### 為什麼設定後仍要重跑 workflow

Secret metadata 無法證明實際權限。只有完整跑過 clone、commit、push 與 PR create/edit，才代表 cross-repo path 真正可用。
